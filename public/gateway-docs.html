Fizzlayer Gateway

Fizzlayer Gateway is one MCP endpoint between your AI agents and the MCP servers they use. It checks every tool call against your rules, can hold a call until you approve it, and hides a tool whose description changes. Use the hosted gateway from /app, or run it yourself with Docker. The routes on this page are also in openapi.json.

Overview

An agent connects to the gateway URL with a Fizzlayer client token. The gateway forwards each MCP request to the right upstream server and asks a policy service about every tools/call and every tools/list answer. The pieces are:

  • The proxy is unmodified agentgateway v1.7.0, pinned by image digest. Fizzlayer does not rebuild that image.
  • fizz-guard is the policy service. It allows, denies, or holds each tool call for approval, pins each listed tool, and writes the audit log. It reads rules, pins, approvals, and token revocations from Postgres on every call.
  • fizz-config renders the agentgateway YAML from a Postgres you run. This is standalone mode.
  • fizz-agent pulls that YAML from the Fizzlayer API with a registration token. This is linked mode, and it is also how the hosted gateway gets its config.
  • The control plane is the API under /api/gateway/*. The app at /app uses the same routes.

The source for all of this is in gateway/ in the repository.

Concepts

Gateway
One MCP endpoint for your account. mode is shared (hosted by Fizzlayer), dedicated, or selfhost. A self-hosted gateway needs public_url, the URL your agents dial.
Server
An upstream MCP server. http and sse take a URL with no username or password in it. stdio takes a command and arguments, and only works on a dedicated or self-hosted gateway on a plan that includes stdio.
Rule
A policy row: an optional server, a tool name or *, an effect, and a notification channel. The app calls the effects Allow (allow), Block (deny), and Ask first (approve). A tool call that matches no rule is denied.
Approval
A held tool call. It records the server, the tool, a SHA-256 hash of the arguments, and the argument key names. Once approved, the same call with the same arguments goes through once.
Pin
A SHA-256 hash of a tool's name, description, and input schema. Its status is unreviewed, approved, or changed.
Client token
An ES256 JWT for one person and one gateway. Agents send it as Authorization: Bearer. Revoking it takes effect on the next call.
Registration token
fizz_reg_…, shown once when a gateway is created or the token is rotated. fizz-agent uses it to pull config. That config can contain upstream API keys, so treat this token like a password.
Audit log
One row per tools/call decision: server, tool, the token's user and id, the argument hash and key names, the decision, and a reason. Argument values are not stored.

Quickstart

Hosted

  1. Sign in at /app and create a gateway. On Hobbyist and Tinkerer it is a shared gateway at https://gw.fizzlayer.com/w/<gateway-id>/mcp.
  2. Add a server from the catalog or by URL. The catalog lists servers from the official MCP Registry that speak streamable HTTP or SSE and need one API key or none. A server that needs an OAuth sign-in cannot be added yet.
  3. Check the server's tools and its rule. A new server starts with an Allow rule for every tool. Change it to Block or Ask first before you connect an agent if you want something stricter.
  4. Open Connect, mint a client token, and copy the setup for your client.

One process serves every active shared gateway. A client token's audience is its own gateway's URL, so a token for one gateway is rejected on another. Shared gateways run http and sse servers only. Dedicated gateways are part of Pro, but none are provisioned yet.

The app asks GET /api/gateway/hosted, and then /gateway-hosted.json, whether the shared host is answering. If it is not, the app still saves your gateway, servers, and rules, and Connect shows how to run the gateway yourself.

An API key you give for a server is encrypted before it is stored. The API decrypts it only to render the config the gateway process pulls, or to list that server's tools when you ask. The config preview in the app leaves it out.

Self-hosted, standalone

You need Docker and a copy of the repository. The compose file builds the Fizzlayer image from the repository, so there is nothing to pull first.

git clone --depth 1 https://github.com/fizzlayer/fizzlayer.git
cd fizzlayer
gateway/compose/test.sh

The script writes gateway/compose/.env with a database password and an admin token, and does not print them. It applies the gateway migrations, runs the row-level security test, and then calls through the proxy with an MCP client. ping is allowed. admin_reset is denied and never reaches the sample server. note disappears from tools/list after its description changes. move_funds is held, approved once, and rejected on the second retry.

The test script removes its containers when it exits. To keep the stack running:

cd gateway/compose
docker compose --env-file .env up -d postgres fizz-config fizz-config-watch fizz-guard sample-mcp agentgateway

The proxy listens on 127.0.0.1:3000. Tokens for this compose file use the audience http://agentgateway:3000/mcp, which is the proxy's name inside the compose network. The approval page is at http://127.0.0.1:9002/. Paste FIZZ_GUARD_ADMIN_TOKEN from .env to use it. That page does not place phone calls. Do not publish port 9002.

With DATABASE_URL=memory://, pins and approvals live in the process and are lost when it exits. The compose file uses Postgres. SQLite is not supported.

Linked mode

In linked mode you run the proxy and fizz-guard, and fizz-agent pulls the config from the Fizzlayer API. The agent polls GET /api/gateway/agent/config with a registration token and writes the file agentgateway watches. Do not point it at the same config.yaml as fizz-config watch, because the two would overwrite each other. More detail is in gateway/README.md.

Create a self-hosted gateway, or rotate its registration token, to get a fizz_reg_… value. It is shown once. The agent never prints the token or the YAML.

fizz-agent environment

FIZZ_API_URLOrigin only, such as https://fizzlayer.com. No path, user, or password.
FIZZ_REGISTRATION_TOKEN_FILEFile containing the token, mode 0600. Preferred.
FIZZ_REGISTRATION_TOKENThe token itself, if you are not using the file.
FIZZ_CONFIG_OUTThe file agentgateway was started with (-f). Default /config/config.yaml.
FIZZ_POLL_SECSSeconds between pulls. Default 5, range 1 to 300.
FIZZ_ADMIN_URLOptional origin of the proxy's admin listener, such as http://127.0.0.1:15000.
FIZZ_AGENT_STATEOptional file for the last ETag. Default .fizz-agent-state next to the config.
 
export FIZZ_API_URL=https://fizzlayer.com
export FIZZ_REGISTRATION_TOKEN_FILE=/run/secrets/fizz-registration
fizz-agent pull

The agent sends Authorization: Bearer, If-None-Match, and ?rev=. A 304 leaves the file alone. A 200 is checked before the file is replaced: it has to be YAML with an mcp listener and one target kind per server. A document that fails the check is not written. The last good file keeps serving, and the agent reports rejected with a short reason to POST /api/gateway/agent/status. The reason never includes the token or the YAML. Network errors, 401, and 5xx also leave the file in place, with a backoff of up to 60 seconds. A bad document does not trigger that backoff, so a fixed revision is picked up on the next poll.

agentgateway watches the file and reloads targets and policies when it changes. If it rejects a reload, it keeps the previous config in memory and its admin listener reports configReload.synchronized: false at GET /api/runtime. When FIZZ_ADMIN_URL is set and answers, fizz-agent reads that flag and puts the previous file back, so a restart does not boot the bad document. The rendered config binds the admin listener to 127.0.0.1:15000 inside the proxy container. Leave FIZZ_ADMIN_URL unset unless the agent can reach that listener without exposing it on the host.

The pulled YAML contains upstream API keys as backendAuth.key.value, because agentgateway reads them from config.yaml. Do not log that file. The preview at GET /api/gateway/gateways/{id}/config leaves keys out, and its ETag ends in -redacted.

The YAML does not carry your rules. It points agentgateway at fizz-guard, and the guard reads rules, pins, approvals, and token revocations from its own database on each call. In linked mode those rows are not synced over the registration token. Edit them in the database your fizz-guard uses. DATABASE_URL=memory:// does not follow rows you change in the app.

The linked compose test runs the same flow against a mock control plane:

gateway/compose/test-linked.sh

It adds a server through the mock, checks that the new tool appears without restarting agentgateway, then serves a bad document and checks that ping still works.

Clients

The gateway speaks streamable HTTP and expects Authorization: Bearer with a client token. Connect in the app fills in your gateway URL and a new token for each client below. With the API, mint a token with POST /api/gateway/gateways/{id}/tokens.

Use the URL you actually dial, and a token whose aud is the gateway's configured public URL. On the hosted gateway those are the same. On the local compose file they differ: you dial 127.0.0.1:3000, and aud is http://agentgateway:3000/mcp.

Claude Code

claude mcp add --transport http fizzlayer YOUR_GATEWAY_URL \
  --header "Authorization: Bearer YOUR_TOKEN"

Claude (web, desktop, and mobile)

In Claude, open Settings, then Connectors, then Add custom connector. Paste the gateway URL, and under Request headers add Authorization with the value Bearer YOUR_TOKEN. Claude connects from Anthropic's servers, so the gateway URL has to be public. 127.0.0.1 will not work.

  }
}

ChatGPT

Not supported yet. ChatGPT's connector form signs in with OAuth or with nothing, and has no place for the token the gateway checks. Fizzlayer does not run an OAuth authorization server. Codex can connect today.

Policies and approvals

Set a rule on the Rules tab, or with PUT /api/gateway/gateways/{id}/policies:

curl -X PUT https://fizzlayer.com/api/gateway/gateways/GATEWAY_ID/policies \
  -H 'Authorization: Bearer SUPABASE_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"tool_name":"*","effect":"approve","notify_channel":"log"}'

tool_name is * or a name matching ^[A-Za-z0-9_.:-]{1,128}$. server_id is optional. Leave it out to cover every server on the gateway. A rule is unique per gateway, server (or every server), and tool name, so a second PUT for the same three updates the existing rule. Leave out notify_channel on an update to keep the current value. A new rule defaults to log.

When the effect is approve, fizz-guard stores a SHA-256 hash of the canonical arguments, rejects the call, and returns right away. The agent sees:

Approval required: an approver was notified (id …). Ask the user to approve, then retry the same call.

The guard does not wait inside agentgateway's 10-second guardrail timeout. An approval expires after 10 minutes by default. On a gateway you run, FIZZ_APPROVAL_TTL_SECS changes that, from 60 seconds to 24 hours.

Approval notification channels
notify_channelWhat happens
logThe guard writes one line: channel, tool, server, short id, and result. No argument values.
webhookThe guard POSTs that summary to FIZZ_APPROVAL_WEBHOOK_URL, an environment variable on fizz-guard, with a 2-second timeout. A URL with a username or password is ignored. If the variable is unset, the guard writes a log line instead. If the POST fails, the approval still exists.
phoneThe guard reserves one call against the account's monthly phone-call cap and returns. It does not dial. The scheduler on the API dials queued calls about once a minute, through AgentPhone, to the account's most recently paired phone number. The call reads the gateway name, the tool, the argument key names, and the approval id, then tells you to approve or deny in the app. It does not take a keypress. If the plan has no calls, the cap is used up, no number is paired, or billing cannot be read, the reservation is recorded as skipped, does not count, and the guard falls back to the webhook or a log line.

Phone approvals need Tinkerer, Pro, or Enterprise, and a US phone number paired on the account. Pairing places a call that reads a 6-digit code, and you enter that code to confirm the number. A number that is not paired is never called.

Decide a pending approval on the Approvals tab, or with the API while it has not expired:

curl -X POST https://fizzlayer.com/api/gateway/gateways/GATEWAY_ID/approvals/APPROVAL_ID/decision \
  -H 'Authorization: Bearer SUPABASE_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"status":"approved"}'

status is approved or denied. args_preview on the list is key names only. An owner or admin can decide. A member can read and gets 403 on writes. A gateway in another account answers 404.

Tool pinning

Every time an upstream server answers tools/list, the guard hashes each tool's name, description, and input schema and compares it with the stored pin.

A server added from the app or the API starts open. It gets an Allow rule for *, and its trust_new_tools flag is on, so the first time the guard sees a tool it pins it as approved. Its tools are listed and callable right away.

Servers added before that default have trust_new_tools off. On those, a tool the guard has not seen is pinned as unreviewed. The gateway's unreviewed_tools setting is hide (the default) or show. hide removes unreviewed tools from tools/list. show leaves them listed. Either way, calling one is denied until its pin is approved.

On every server, if a later list has a different hash for a tool, the tool is removed from that answer, its status becomes changed, calls to it are denied, and one open pin alert is stored. The alert shows up on the Changes tab. Its description_preview is up to 200 characters of text from the MCP server. Read it as untrusted input.

curl -X POST https://fizzlayer.com/api/gateway/gateways/GATEWAY_ID/pins/approve \
  -H 'Authorization: Bearer SUPABASE_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"server":"sample","tool":"note"}'

Approving copies the observed hash onto the pin, sets the status to approved, and acknowledges open alerts for that tool. PATCH the gateway with {"unreviewed_tools":"hide"} or "show" to change the default.

On a gateway with more than one server, agentgateway names each tool {server}_{tool}. The guard uses that prefix to tell which server a tool belongs to.

Client tokens and JWKS

GET /api/gateway/jwks is public and needs no session. agentgateway checks every request with jwtAuth in strict mode: issuer fizzlayer, audience equal to the gateway's public URL, and keys from GATEWAY_JWKS_URL, or from the request origin plus /api/gateway/jwks.

Claims are iss, sub (your user id), aud, ws (your workspace id), jti, iat, and exp. The algorithm is ES256.

curl -X POST https://fizzlayer.com/api/gateway/gateways/GATEWAY_ID/tokens \
  -H 'Authorization: Bearer SUPABASE_ACCESS_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"name":"Cursor on laptop","ttl_seconds":3600}'

The JWT is returned once and is not stored. Fizzlayer keeps its name, id, expiry, and revocation time. The default life is 1 hour. ttl_seconds can be 60 to 2592000 (30 days). The name is 1 to 80 characters. DELETE /tokens/{token_id} revokes a token, and the guard refuses it from the next call on.

Each server's auth_kind is none, key, or passthrough. Send api_key with key. The key is sealed with AES-256-GCM before it is stored, using a key held by the API process and not kept in the database. The server list reports has_secret and never returns the key. passthrough uses agentgateway's backend-auth passthrough.

Control-plane API

Signed-in routes take a Supabase access token as Authorization: Bearer, or the fizz_supabase cookie the site sets when you sign in. Your workspace is created on first use, and you are its owner. Owners and admins can change a gateway. Members can read it.

If you leave out mode on create, the API uses shared on Hobbyist and Tinkerer, and dedicated on Pro and Enterprise. The stored URL is https://gw.fizzlayer.com/w/{id}/mcp for a shared gateway and https://{name}.gw.fizzlayer.com/mcp for a dedicated one. Dedicated hosts are not provisioned yet.

Errors use one JSON shape with a stable code. Over a plan limit, the API answers 402 with gateway_limit, server_limit, stdio_not_included, or dedicated_not_included. A stdio server on a shared gateway is 400 stdio_shared. A name or body that fails validation is 400 invalid_request. Too many requests is 429 rate_limited with Retry-After: 60.

Running the control plane yourself

If you deploy the API from this repository, apply the gateway migrations with supabase db push. Until 20261114000400_gateway_control_plane.sql is applied, these routes answer 503. Set these on the API, and do not commit the values:

  • GATEWAY_SIGNING_KEY: a PKCS#8 PEM for the ES256 key that signs client tokens and backs the JWKS. The server does not generate one. A single-line value may use \n for line breaks.
  • GATEWAY_SECRET_KEY: base64 of 32 bytes, used to encrypt stored MCP API keys.
  • GATEWAY_JWKS_URL: the absolute JWKS URL written into the YAML. Optional, but set it in production.
  • GATEWAY_GUARD_HOST: host:port of fizz-guard. Default fizz-guard:9001. In the single hosted container, use 127.0.0.1:9001.
  • GATEWAY_FLEET_TOKEN: fizz_fleet_ plus 64 hex characters, for the hosted fleet pull. The same value is FIZZ_FLEET_TOKEN on the fleet.
  • GATEWAY_HOSTED: set to 1, true, or yes once the shared fleet is running. Anything else keeps /api/gateway/hosted at {"available":false}.

The rendered YAML sets adminAddr to 127.0.0.1:15000, the session key to disabled, statefulMode: stateless, prefixMode: conditional, and mcpGuardrails with failureMode: failClosed on the tools/call request and the tools/list response.

Limits

These are the plan columns on fizz_plans, the same numbers as the pricing page. Monthly counts reset on the first of each month (UTC).

What is enforced:

  • Gateway count, server count, stdio, and dedicated mode are checked when you create a gateway or add a server.
  • fizz-guard rejects a tool call past the monthly tool-call number and records it in the audit log with decision quota.
  • Phone approvals count against one monthly call cap per account. Pairing calls do not count. Enterprise is unlimited unless the contract sets a cap.
  • The scheduler deletes audit rows older than your plan's audit days. Retention follows your current plan, so moving to a plan with fewer days deletes older rows at the next run. Enterprise rows are kept unless a contract says otherwise. Daily usage counts are kept for metering.
  • When you move to a plan with lower limits, the newest gateways and servers over the new limit are paused, not deleted.
  • The hosted shared process also limits requests per gateway per minute: Hobbyist 30, Tinkerer 120, Pro 240, and Enterprise 600.
  • The control-plane API allows 120 reads and 60 writes a minute per user, and 30 tool listings a minute.

Not enforced yet: the seat number (there is no way to add members yet), and usage-based billing. Stripe does not receive gateway usage records.

Troubleshooting

401
The session token was missing or rejected, or a registration token was rejected on an agent route. Sign in again, or rotate the registration token.
402
gateway_limit, server_limit, stdio_not_included, or dedicated_not_included. Remove a gateway or server, or move to a plan that includes what you asked for.
409 gateway_disabled
The gateway is paused because it is over your plan's limit. Remove another gateway or upgrade, and it runs again.
503 from /api/gateway
The database could not be reached. On a control plane you run yourself, the gateway migrations may not be applied, or GATEWAY_SIGNING_KEY or GATEWAY_SECRET_KEY may be missing.
503 missing_secret on a server
That server's stored key could not be decrypted, so the gateway leaves the server out and keeps serving its other servers. Remove the server and add it again with its key.
A tool is missing from tools/list
Its description or schema changed, or it is unreviewed and the gateway hides unreviewed tools. Check the Changes tab and approve the pin. Read description_preview as untrusted text.
Every call is denied
No rule allows the call, or the tool's pin is not approved. A tool call with no matching rule is denied. The guard also fails closed, so if it cannot answer, the call is denied.
tools/call says approval is required
Approve that id, then retry with the same arguments before it expires. Different arguments make a new approval. An approval works once.
The client connects and the token is rejected
The token's aud must match the gateway's public URL. For the local compose file that is http://agentgateway:3000/mcp, even though you dial 127.0.0.1:3000. Check that the token has not expired or been revoked.
A phone approval did not ring
Hobbyist does not include calls. The month's cap may be used up, or no number is paired. The guard only reserves the call, and the scheduler dials it about a minute later. A skipped reservation does not use up the cap. On a control plane you run yourself, AGENTPHONE_API_KEY must be set, and AGENTPHONE_AGENT_ID too if the AgentPhone account has more than one agent.
A long SSE stream closes on the hosted gateway
Hosted traffic passes through Vercel, which can close a stream when its time limit is reached. The gateway is still running. Reconnect.
The catalog does not load
502 registry_unavailable means the MCP Registry did not answer. Try again, or add the server by URL.
The proxy will not load the config
In standalone mode, fizz-config refuses to write a credential and refuses stdio on a shared gateway. Check the container logs.

Security

  • The guard fails closed. If it is down or returns an error, agentgateway denies the call.
  • The guard never receives the client's Authorization or Cookie header.
  • Stored MCP API keys are encrypted with AES-256-GCM. The encryption key lives with the API process, not in the database. The browser never receives a stored key.
  • Registration tokens are stored only as SHA-256 hashes. Client tokens are not stored at all.
  • The pulled config can contain upstream API keys. The preview in the app does not. Do not log either.
  • Client tokens are bearer secrets. Prefer a short life. Revocation works because the guard checks it on each call, not because the YAML changes.
  • Listing a server's tools from the API only calls public addresses, so a server URL cannot be used to reach a private network.
  • Shared gateways cannot run stdio. A dedicated or self-hosted gateway can, and this repository does not sandbox that process. Treat a stdio server as a command you are willing to run.
  • Do not publish the proxy's admin listener. The rendered config binds it to 127.0.0.1:15000. Do not publish port 9002 either: its admin token can decide every pending approval in that database.
  • Webhook URLs with a username or password are ignored. Pin alert text comes from the MCP server, so it is untrusted if the server is.
  • The gateway does not prevent prompt injection. A tool result can still instruct the model. What the gateway controls is whether the next tool call is allowed.
